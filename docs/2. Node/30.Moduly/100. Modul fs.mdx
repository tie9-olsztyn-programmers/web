tsconfig.json Configuration Breakdown:


target ("ES2022"): Sets the JavaScript language version for emitted code, ensuring compatibility with modern Node.js features.


module ("NodeNext"): Specifies the module system for the compiled code, supporting both modern ES Modules (import/export) and CommonJS (require).


moduleResolution ("NodeNext"): Aligns how TypeScript looks up imported files with Node.js's native module resolution algorithm.


rootDir ("./src"): Defines the root folder of your source files, ensuring the folder structure inside outDir stays flat and predictable.


outDir ("./dist"): Specifies the output directory where all compiled .js files will be placed.


strict (true): Enables a wide range of strict type-checking behaviors for higher code safety (e.g., strictNullChecks, noImplicitAny).


esModuleInterop (true): Fixes compatibility issues when importing CommonJS packages into ES Modules using standard default imports.


skipLibCheck (true): Skips type checking of declaration files (.d.ts) inside node_modules to significantly speed up compilation.


include (["src/**/*"]): Tells the compiler to only process files located inside the src directory.


exclude (["node_modules", "dist"]): Prevents TypeScript from compiling external dependencies or already compiled output files.

:::


:::tip

Why Add "types": ["node"] and @types/node:


TypeScript vs. Runtime: Node.js and tsx know how to execute built-in modules like node:fs at runtime, which is why your app runs fine. However, the TypeScript compiler (tsc) and your IDE only know standard JavaScript by default—they need @types/node to understand Node-specific APIs (fs, process, Buffer).


Explicit Global Types ("types": ["node"]): By default, TypeScript automatically scans and includes all @types/* packages installed in node_modules/@types. Explicitly setting "types": ["node"] tells the compiler and IDE to load only Node.js global type definitions, preventing global namespace pollution from other third-party libraries and speeding up type checking.

Why You Need "type": "module" in package.json:


Native ES Modules (import/export): By default, Node.js treats .js and .ts files as legacy CommonJS (require). Adding "type": "module" tells Node.js to interpret your files as modern ES Modules right from the start.

Important Rule for Local Imports: In native ES Modules, you must explicitly include the .js file extension when importing local project files (e.g., `import { helper } from "./utils.js"`), even when writing the code inside .ts files.

```typescript title="src/index.ts"

import fs from "node:fs";

import fsp from "node:fs/promises";


// Type Guard (Functional Predicate) for safe system error handling

function isErrnoException(e: unknown): e is NodeJS.ErrnoException {

    return e instanceof Error && "code" in e;

}


async function runXFilesInvestigation(): Promise<void> {

    console.log("=== [1] OPENING FBI BASEMENT OFFICE ===");


    // --- PART A: SYNCHRONOUS (BLOCKING) OPERATIONS ---

    console.log("[2] Mulder starts writing case-1013.txt (SYNC)...");

    fs.writeFileSync("case-1013.txt", "I Want to Believe");

    console.log("[3] Mulder overwrites case-1013.txt (SYNC)...");

    fs.writeFileSync("case-1013.txt", "The Truth Is Out There");


    const syncContent = fs.readFileSync("case-1013.txt", "utf-8");

    console.log(`[4] Scully reads SYNC file immediately: "${syncContent}"`);


    // --- PART B: ASYNCHRONOUS WITH CALLBACK (NON-BLOCKING) ---

    console.log("[5] Delegating Roswell report to assistant (ASYNC CALLBACK)...");

    fs.writeFile(

        "roswell-1947.txt",

        "Subject: Unidentified Flying Object recovered in New Mexico.",

        (err) => {

            if (err) {

                console.error("Transmission error:", err);

                return;

            }

            console.log("[9] --> CALLBACK FINISHED: roswell-1947.txt saved!");

        }

    );


    // --- PART C: ASYNCHRONOUS WITH PROMISES (NON-BLOCKING) ---

    console.log("[6] Firing parallel UFO sighting logs (ASYNC PROMISES - NO AWAIT)...");

    logSighting("Sighting #1: Triangle craft hovering over Area 51");

    logSighting("Sighting #2: Crop circles reported in Oregon");


    console.log("[7] Main thread reaches the end of synchronous flow! Waiting for background tasks...");


    // --- PART D: SEQUENTIAL ASYNC (WITH AWAIT) ---

    await createVaultAndCleanup();

    console.log("=== [11] INVESTIGATION CLOSED ===");

}


async function logSighting(anomaly: string): Promise<void> {

    const timestamp = new Date().toLocaleString("en-GB");

    const line = `[[${timestamp}]] X-FILE LOG: ${anomaly}\n`;

    try {

        await fsp.appendFile("sightings.txt", line);

        console.log(`[8] --> PROMISE APPENDED: ${anomaly}`);

    } catch (err) {

        console.error("Append error:", err);

    }

}


async function createVaultAndCleanup(): Promise<void> {

    try {

        // Creating nested directories

        await fsp.mkdir("x-files-vault/sector-7", { recursive: true });

        const files = await fsp.readdir(".");

        console.log("[10] Active files in sector before Syndicate sweep:", files);


        // The Syndicate Cover-Up: deleting evidence safely

        await fsp.unlink("case-1013.txt");

        await fsp.rm("x-files-vault", { recursive: true, force: true });

    } catch (err: unknown) {

        if (isErrnoException(err) && err.code === "ENOENT") {

            console.log("Evidence already wiped by the Cigarette Smoking Man.");

        } else {

            console.error("System error:", err);

        }

    }

}


runXFilesInvestigation();

```

## 2. Deconstructing the Investigation: The 4W2H Breakdown


To understand what just happened in our FBI mainframe, let's deconstruct the code step-by-step **according to the 4W2H model**, blending in core programming paradigms and **SOLID** principles.


### 1. WHAT (The Domain: Primitives vs. Complex Objects vs. DTOs)

What kind of data is travelling between our TypeScript code and the hard drive?

- **Primitives (`string`):** When Mulder writes `"The Truth Is Out There"` or Scully reads `syncContent` using `"utf-8"`, our domain operates on simple string primitives.

- **Raw Binary Buffers (`Buffer`):** If you forget the `"utf-8"` parameter in `fs.readFileSync("case-1013.txt")`, Node.js returns a complex object: `<Buffer 54 68 65 20 54 72 ...>`. Hard drives don't speak English; they speak raw bytes. `"utf-8"` acts as our translator.

- **System Error Objects (`NodeJS.ErrnoException`):** When an operation fails (e.g., deleting a non-existent file), Node throws a specialized object containing system metadata like `err.code` (`ENOENT`, `EACCES`).


:::tip ENOENT and other FBI System Error Codes

- `ENOENT` (*Error NO ENTry*) – No such file or directory (the truth has been hidden).

- `EACCES` (*Error ACCESs*) – Permission denied (requires Level 4 Security Clearance).

- `EEXIST` (*Error EXIST*) – File or directory already exists (when calling `mkdir` without `recursive: true`).

- `EBUSY` (*Error BUSY*) – Resource is locked by another process.

:::


### 2. WHERE (State & Storage: Local Variables vs. Global State vs. Databases)

Where does our investigation data live?

- **Local Variables:** Variables like `syncContent` or `line` live inside the local function scope on the RAM stack/heap.

- **Flat-File Storage (Pre-Database State):** Files like `case-1013.txt` and `sightings.txt` live directly on the **Operating System's File System**. Think of the File System as the ancestor of all databases—a persistent cabinet of raw folders and files managed by the OS kernel.


### 3. WHEN (Evaluation Strategies: Eager vs. Lazy & Blocking vs. Non-Blocking)

This is the heart of Node.js architecture. Node.js runs on a **single thread** (imagine a single FBI agent sitting at one desk).


| Dimension | Synchronous (`writeFileSync`) | Asynchronous (`writeFile` / `fsp.appendFile`) |

| :--- | :--- | :--- |

| **Execution** | **Blocking (Eager Wait)** – stops the entire CPU thread until the disk platters finish spinning. | **Non-Blocking (Deferred)** – initiates the I/O task and immediately moves to the next line of code. |

| **FBI Metaphor** | Mulder puts a page in the fax machine and **stares at it motionlessly for 5 minutes** until the confirmation prints. Nobody can talk to him. | Mulder hands the document to an intern to fax and **immediately goes back to chasing aliens**. The intern knocks on his door when it's done. |

| **Evaluation** | Promises in `node:fs/promises` are **Eagerly Evaluated**—the moment you call `logSighting()`, the disk operation starts immediately in the background (even without `await`!). | The callback function `(err) => { ... }` is evaluated **lazily/later** by the Event Loop, only after the OS signals completion. |


### 4. WHO (Data Flow: Pull Model vs. Push Model Dynamics)

Who is in charge of moving data between the disk and our code?

- **Pull Model (Synchronous & `await`):** In `const syncContent = fs.readFileSync(...)`, our code is the boss. It reaches out, grabs the thread by the collar, and **pulls** the data directly into the variable before allowing the program to breathe.

- **Push Model (Asynchronous Callbacks):** In `fs.writeFile("roswell-1947.txt", ..., (err) => {})`, our code surrenders control (Inversion of Control). We give Node.js a callback function and say: *"Don't call us, we'll call you."* When the hard drive finishes, the Node.js **Event Loop pushes** the result (or error) into our callback.


### 5. HOW (Reactivity: Regular Variables vs. Reactive State/Broadcasters)

How does our application react to changes?

- In `syncContent`, we use a **regular variable**—it holds a static snapshot of the text at the exact millisecond it was read. If the Cigarette Smoking Man edits `case-1013.txt` two seconds later, `syncContent` has no idea.

- In our asynchronous `fs.writeFile` and `Promise` chains, we see **one-shot asynchronous notification**: the Event Loop acts as an internal broadcaster that notifies our pending Promise or Callback once the I/O state transitions from *Pending* to *Fulfilled/Rejected*.


### 6. HOW LONG (Lifecycle: Volatile In-Memory vs. Persistent Storage)

How long does the evidence survive?

- **Volatile In-Memory (RAM):** `const syncContent` and `const files` live only for a few milliseconds. The moment `runXFilesInvestigation()` finishes (`[11]`), the Garbage Collector vaporizes them like a Men in Black neuralyzer.

- **Persistent Storage (Disk):** `roswell-1947.txt` and `sightings.txt` survive long after the Node.js process terminates, power is cut, or the computer reboots—unless explicitly destroyed via `fsp.unlink()` or `fsp.rm()`.

## 3. Programming Paradigms & SOLID Principles in Action


Even in a 60-line script, several foundational paradigms and **SOLID** principles are at play:


1. **Imperative & Procedural Paradigm (`PART A`):** Step-by-step instructions mutating external state (`writeFileSync` -> `writeFileSync` -> `readFileSync`).

2. **Functional Programming Paradigm:**

- **Higher-Order Functions (HOF):** `fs.writeFile` accepts a function (callback) as an argument.

- **Pure Type Predicate (`isErrnoException`):** A deterministic, side-effect-free function that narrows `unknown` to `NodeJS.ErrnoException`.


:::note Type Guard Explained (`isErrnoException`)

```typescript

function isErrnoException(e: unknown): e is NodeJS.ErrnoException {

    return e instanceof Error && "code" in e;

}

```

Why not just write `catch (err: any)`? Because `any` turns off TypeScript's radar, letting alien bugs slip through!

- `e: unknown` – forces us to verify the type before touching its properties.

- `e is NodeJS.ErrnoException` – a **type predicate**. If the function returns `true`, TypeScript narrows the type inside the `if` block, giving us full autocomplete for `err.code`.

:::


3. **Single Responsibility Principle (SRP - the 'S' in SOLID):** Notice how we extracted `isErrnoException` (error verification) and `logSighting` (formatting + appending) into separate functions. Each function has one clear reason to change.

4. **Dependency Inversion Hint (the 'D' in SOLID):** Right now, our `logSighting` function is tightly coupled to `node:fs/promises`. In a massive enterprise FBI system, we would inject a `StorageLogger` interface instead, allowing us to swap the file system for an SQL database without rewriting our business logic.

## 4. Pattern Comparison: The Evolution of Asynchronous I/O


Why does Node.js have *three* ways to write a file (`writeFileSync`, `writeFile` with callbacks, and `fsp.writeFile` with Promises)? Let's compare them side-by-side.


| Approach | Code Readability | Thread Behavior | Error Handling | The X-Files Verdict |

| :--- | :--- | :--- | :--- | :--- |

| **1. Synchronous (`fs.writeFileSync`)** | High (linear) | **Freezes the entire app** during disk I/O. | Standard `try / catch` | Great for loading a config file at startup; **fatal** inside an HTTP server with 1,000 users. |

| **2. Error-First Callbacks (`fs.writeFile`)** | Poor (leads to deeply nested **"Callback Hell"**) | Non-blocking (fast) | Manual `if (err) return;` inside every callback | Legacy pattern from 2011. Avoid in new TypeScript projects. |

| **3. Promises / `async-await` (`node:fs/promises`)** | **High** (looks linear like sync, acts like async) | **Non-blocking** (fast & scalable) | Unified `try / catch` blocks | **The Modern Standard.** Combines the readability of sync with the performance of async. |


:::warning The Parallel Race Condition Trap!

Look back at `[6]` in our code:

```typescript

logSighting("Sighting #1: Triangle craft..."); // No await!

logSighting("Sighting #2: Crop circles...");   // No await!

```

Because we fired both `async` functions **without `await`**, both disk operations race each other in the background (**Race Condition**). Node.js does **NOT** guarantee which sighting will be written to `sightings.txt` first! If chronological order is critical for Scully's court testimony, always `await` them sequentially:

```typescript

await logSighting("Sighting #1...");

await logSighting("Sighting #2...");

```

:::

## 5. Software Design Patterns Under the Hood


When you use `node:fs`, you are interacting with three classic Software Design Patterns built right into Node.js:


### 1. The Continuation-Passing Style (CPS) / Error-First Callback Pattern

Instead of returning a value via `return`, `fs.writeFile(path, data, callback)` passes the result forward into a continuation function. Notice the signature: `(err, result) => {}`. The **first parameter is always reserved for an error** (`null` if successful). This forces developers to acknowledge that disk I/O can fail at any moment.


### 2. The Proxy / Adapter Pattern (`node:fs/promises`)

Under the hood, the operating system's C++ bindings (libuv) work on low-level asynchronous callbacks. The `node:fs/promises` API acts as an **Adapter** that wraps those raw callback operations into modern ECMAScript `Promise` objects, allowing you to use clean `async/await` syntax instead of nested callbacks.


### 3. The Guard Clause & Type Guard Pattern

In both our callback (`if (err) return;`) and our `catch` block (`if (isErrnoException(err) && err.code === "ENOENT")`), we use **Guard Clauses** to immediately handle edge cases and narrow unknown runtime states into strictly typed contracts before executing the rest of the logic.

## 6. Summary & Knowledge Check


### Lesson Summary

- **`node:fs`** provides both synchronous (`...Sync`) and asynchronous (`callback` and `Promise`) methods for file and directory manipulation.

- **According to our 4W2H model**, synchronous methods use a **Blocking Pull** strategy (halting the single Node thread), while asynchronous methods use a **Non-Blocking** strategy that transforms **Volatile RAM data** into **Persistent Disk Storage** without freezing the application.

- Always prefer **`node:fs/promises`** with `async/await` and protect your `catch (err: unknown)` blocks using a **Type Guard** (`isErrnoException`) instead of `any`.
